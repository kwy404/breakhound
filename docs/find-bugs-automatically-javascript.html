How to find bugs automatically in a JavaScript library

Most libraries are tested with the inputs their authors imagined, and the bugs live in the ones nobody did. breakhound points at a package, generates the awkward inputs for you and hands back a reproduction and a ready Vitest test for every bug it finds.

Why library bugs hide from your test suite

A hand written test encodes what the author already believes. You test truncate("hello world", 5) because that is the example in your head. You do not test a string that ends in an emoji, a negative number between -1 and 0, or a date that is one second after a daylight saving jump, because you do not think of them. Those are exactly the inputs real users send.

To find bugs automatically you need two things: a way to produce hostile but valid inputs for every function, and a set of rules that say what a correct result looks like without knowing the specific answer. The rules are called invariants. "A string function never returns half of a surrogate pair" is an invariant. "The same input gives the same output in every time zone" is another.

The problem is that String.prototype.slice counts UTF-16 code units, not characters. An emoji such as '\u{1F600}' occupies two code units (a surrogate pair). Cut after the first one and you return a lone high surrogate, which is not valid text. It renders as a replacement character and makes encodeURIComponent throw a URIError. Run breakhound on the library

You do not need to write a harness. Give breakhound an npm package name or a path to a local folder:

It reads the TypeScript declarations (.d.ts) to learn the type of each parameter, then generates inputs for every exported function. Strings get emoji, combining marks and lone surrogates. Dates get daylight saving transitions and dates before 1970. Numbers get -0, NaN, Infinity and values between -1 and 0. These edge cases come from the edgegoat package. The invariants it checks

breakhound ships a fixed set of oracles. Each maps to a rule id you can select with --rules:

Rule idWhat it catches
lone-surrogate-outputOutput strings split in the middle of an emoji
timezone-dependentResults that change with the TZ value (see time zone bugs)
unexpected-crashExceptions on inputs that match the declared types
nan-leakNaN returned for finite input
roundtripPairs such as encodeX and decodeX that do not invert each other
not-idempotentNormalize style functions that change their own output
negative-zero-signValues between -1 and 0 that lose the minus sign
nondeterministicDifferent results for the same input

Each call runs in an isolated child process with a timeout, and the time zone rules run under several TZ values (six by default, including UTC, America/Sao_Paulo, Pacific/Kiritimati and America/New_York). Runs are seeded, so seed 42 gives the same inputs every time.

Narrow the run and gate your pipeline

On a large package you usually want to focus. Use --only and --exclude with wildcards, pick rules with --rules, and raise the budget with --max-calls when a first pass is clean. To fail a build when something serious shows up, use --fail-on:

In GitHub Actions breakhound emits annotations and writes a markdown job summary on its own. The full setup is in automated testing in GitHub Actions. If you would rather write properties by hand for the same kind of checks, see property based testing without writing tests.

breakhound executes the package code it analyzes. Run it on code you trust, or inside a container. Installs use --ignore-scripts, and the child process isolation is for robustness, not a security sandbox.

The approach has paid off on real projects. Fixes merged upstream include relative-time-element (a year check used UTC instead of the display time zone), budoux and vscode-js-debug (surrogate pairs split) and pdf.js (negative numbers above -1 lost their sign).

FAQ

Do I need to write tests before I can find bugs automatically?

No. breakhound derives inputs from the type signatures in your .d.ts files and checks built in invariants, so a library with no tests at all can still be scanned with npx breakhound ./my-lib.

Does it only work on TypeScript projects?

It works on JavaScript and TypeScript libraries. Types give it better inputs, so a package that ships declarations gives the most precise results.

How many false positives should I expect?

Each finding carries a severity and a confidence level, so you can triage the high confidence ones first. Treat a finding as a question: either the function should handle that input, or its types are too loose.

Can I get the same result every run?

Yes. The default seed is 42, and you can change it with --seed. The run is also saved to .breakhound/last-run.jsonl and .breakhound/report.json unless you pass --no-save.

How is this different from fuzzing?

Coverage guided fuzzers such as Jazzer.js mutate bytes to find crashes and need a fuzz target. breakhound uses typed edge cases and checks semantic invariants such as time zone independence and sign preservation. The fuzz testing TypeScript guide compares them in detail.
