Case file G-03Dates and time

Timezone bugs in JavaScript and how to catch them

A JavaScript Date is one instant, but every getter answers in some time zone. Mix two of them and your code is right on your laptop and wrong for half the planet.

#Why timezone bugs in JavaScript are so common

Instant vs wall time

A Date is one instant. Year, month and hour only exist once you pick a zone.

A Date stores a single number: milliseconds since 1970-01-01T00:00:00Z. Everything else is interpretation. getFullYear(), getMonth() and getHours() interpret that number in the host time zone, set by the TZ environment variable on Node or the operating system in a browser. getUTCFullYear() and friends interpret it in UTC. Intl.DateTimeFormat and toLocaleString use the host zone unless you pass timeZone.

That gives you at least three answers to the question "what year is this?", and they disagree for a few hours every day. Your laptop runs in one zone, your CI runner usually runs in UTC, and your users are everywhere. A test that passes locally and fails in CI, or the reverse, is the classic symptom.

#Daylight saving time breaks "one day equals 24 hours"

#Dates before 1970 and negative timestamps

Case 02

Time zone dependence. The recorded case catches yearLabel(0) answering 1969 in four zones.

Timestamp zero is midnight UTC on January 1, 1970. Anything west of UTC sees that instant as December 31, 1969. That makes timestamp zero, and small negative timestamps, a perfect probe for zone-dependent code. Negative values also expose rounding mistakes, for example when someone uses Math.floor on one side and integer division on the other.

This function is fine as long as everyone agrees it means "the year in the host zone". It is a bug when callers expect a stable answer for the same input, which is what a pure function with a number argument promises. Call it with 0 in UTC and you get 1970. Call it in America/Sao_Paulo and you get 1969. Either take a timeZone argument or use getUTCFullYear() and document it.

#How breakhound catches timezone bugs

Pick the zones

--zones UTC,Asia/Tokyo replaces the six default zones. The first one is the reference.

You do not have to remember which instants are dangerous. breakhound reads the TypeScript types of your package and generates inputs for every parameter, including date edge cases from the edgegoat package: time zone boundaries, DST transitions and dates before 1970. Each function runs in an isolated child process under several TZ values (six by default, including UTC, America/Sao_Paulo, Pacific/Kiritimati and America/New_York). If the result changes only because the host zone changed, it reports a timezone-dependent finding.

Every finding comes with a minimal reproduction script and a ready-made test that sets TZ itself, so you can paste it into your suite:

Runs are seeded (default seed 42), so the same command gives the same findings. Read how to find bugs automatically in JavaScript for the full workflow, and automated testing in GitHub Actions to run it on every pull request.

Handle with care

breakhound executes the package code it analyzes. Run it on code you trust, or inside a container.

#A checklist that prevents the bug

  • Choose one zone per operation and use it for both comparison and display.
  • Pass timeZone explicitly to Intl.DateTimeFormat and toLocaleString when the zone matters.
  • Use calendar setters (setDate, setMonth) for calendar math, not millisecond constants.
  • Test with at least UTC, a zone west of UTC, a zone far east, and a zone with DST.
  • Include timestamp 0, negative timestamps and the last hours of December 31 in your fixtures.

Unicode edge cases cause a similar class of silent failures, covered in surrogate pair bugs.

#Questions on the record

Q1Why does my date test pass locally but fail in CI?

CI machines usually run in UTC while your laptop runs in your local zone. Any code that mixes UTC and local getters behaves differently between the two. Set TZ explicitly in the test and run it under more than one zone.

Q2Which time zones should I test?

At least UTC, one zone west of UTC such as America/New_York, one far east such as Pacific/Kiritimati, and a zone with daylight saving time. breakhound uses six zones by default.

Q3Should I use getUTC methods everywhere?

No. Use UTC for storage and comparisons between instants, and the viewer's zone for display. The bug is mixing the two inside one decision, not using either one.

Q4Does setting process.env.TZ at runtime work in Node?

On modern Node versions, yes, assigning process.env.TZ updates the zone for later date calls. The generated tests rely on that, and restore the original value afterward.

Q5Can breakhound check functions that take callbacks or Date objects?

Yes. It generates inputs from your .d.ts types, including dates and generated callbacks, then compares results across zones.
