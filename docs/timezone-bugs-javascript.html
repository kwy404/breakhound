Time zone bugs in JavaScript and how to catch them

A Date in JavaScript is a single instant, but every getter answers in some time zone. getFullYear answers in the host zone, getUTCFullYear in UTC, and Intl.DateTimeFormat in whatever zone you pass. Mix two of them and your code is correct on your laptop and wrong for half the planet.

A real example

In github/relative-time-element#384 the year check used UTC while the date was displayed in the user's zone. Around New Year, users saw the wrong format. A simplified version of that bug class:

format.ts
export function label(date: Date, now: Date) {  // bug: compares the UTC year, but displays local time  if (date.getUTCFullYear() === now.getUTCFullYear()) {    return date.toLocaleDateString("en", { month: "short", day: "numeric" });  }  return date.toLocaleDateString("en");}

How breakhound catches it

breakhound calls every function with the same arguments under several TZ values, such as UTC, America/Los_Angeles and Asia/Tokyo, in separate child processes. If the output differs only because the host zone changed, it reports output depends on host time zone with the exact instant that triggers it. Inputs include DST transitions, year boundaries and dates before 1970, where negative timestamps expose rounding bugs.

terminal
npx breakhound ./my-date-lib

How to fix it

  • Pick one zone per operation and use it for both comparison and display.
  • Pass timeZone explicitly to Intl.DateTimeFormat when the zone matters.
  • Lock the zone in tests with TZ and run the suite under more than one zone.

FAQ

Why does my date test pass locally but fail in CI?
CI machines usually run in UTC while your laptop runs in your local zone. Any code that mixes UTC and local getters will behave differently.
Which time zones should I test?
At least UTC, one zone west of UTC and one far east such as Asia/Tokyo, plus a zone with DST.
