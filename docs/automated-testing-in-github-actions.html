Case file G-04CI

Running breakhound in GitHub Actions

A pull request check that finds crashes, time zone bugs and broken Unicode handling in your JavaScript library takes about ten lines of YAML. Here is the workflow, what it reports, and how to keep runs reproducible.

#Why add a bug hunt to CI

Gate

A CI step that fails the build when a rule is broken, so the bug never reaches main.

Unit tests only cover the cases someone thought of. A type driven check covers the rest: npx breakhound reads your TypeScript declarations, generates inputs for every parameter (including time zones, DST edges, emoji, lone surrogates, -0, NaN and empty strings), and checks invariants on the results. Running it in CI means a regression is caught on the pull request that introduces it, not in a bug report six months later. For how the checks work, see the eight case files on the home page.

#The workflow people write first

The first attempt usually has two problems. npm install runs lifecycle scripts of every dependency, and || true swallows the exit code, so the job is green no matter what was found. A check that can never fail is decoration.

#A workflow that fails on real bugs

One step

npx breakhound . --fail-on high after npm ci --ignore-scripts.

Install with npm ci --ignore-scripts for a reproducible dependency tree without running install scripts, then gate on severity with --fail-on. The process exits with code 1 when a finding has that severity or higher, which fails the job.

Start with --fail-on high (lone surrogates, crashes, time zone dependence) and tighten to medium once the backlog is clean. If your package entry point is a build output, add your build step before the breakhound step so the declarations and code exist.

Handle with care

breakhound executes the code it analyzes. That is fine for your own repository. For pull requests from forks, keep permissions minimal as above, expose no secrets to the job, and avoid pull_request_target.

#Keeping the evidence: JSON, JSONL and artifacts

A red check is more useful when the reproduction scripts and Vitest tests are one click away. Use --json --output report.json to write the full report to a file, --log to write a JSON Lines run log (the BREAKHOUND_LOG environment variable works too), and upload both with actions/upload-artifact. By default breakhound also saves .breakhound/last-run.jsonl and .breakhound/report.json unless you pass --no-save.

The if: always() guards matter: without them the later steps are skipped exactly when the gate step fails, which is when you want the files.

#Failing only on new bugs

Regressions only

--baseline baseline.json --fail-on high fails on new findings, not on old ones.

An older library may already have findings that nobody can fix this week. Save a report from your main branch, then pass it with --baseline. breakhound lists which findings are new and which were fixed since that report, and --fail-on then counts only the new ones, so the job fails on regressions instead of on the backlog.

The same flag compares two published versions of a package: save a report for my-lib@1, then run npx breakhound my-lib@2 --baseline my-lib-1.json. On your own machine, --baseline last compares with the previous run saved in .breakhound/report.json.

#Seeds and reproducibility

Reproducible

A fixed seed and call budget make the same commit find the same bugs on every runner.

Input generation is seeded. The default seed is 42, so two runs on the same commit explore the same inputs. That is what you want on pull requests: a failure should not vanish on rerun. To widen coverage over time, run a scheduled workflow that passes a different seed, such as --seed ${{ github.run_number }}, and use the seed printed in the log header to rerun locally:

You can also narrow a noisy run with --only, --exclude or --rules, and bound it with --max-calls and --timeout. Related reading: time zone bugs in JavaScript, which breakhound exercises by running under several TZ values, and negative zero bugs. See the home page for the full flag list.

#Questions on the record

Q1How do I make the GitHub Actions job fail on findings?

Pass --fail-on high (or medium, low, info). The command exits with code 1 when a finding of that severity or higher exists.

Q2Where does the job summary come from?

In GitHub Actions breakhound appends a markdown report to GITHUB_STEP_SUMMARY automatically and emits annotations. You do not enable it.

Q3Why use npm ci --ignore-scripts?

npm ci installs exactly what the lockfile says, and --ignore-scripts skips dependency lifecycle scripts. breakhound installs npm packages with --ignore-scripts as well.

Q4Will the same commit give the same findings on every run?

That is the point of seeding. The default seed is 42; pass --seed to choose another one and record it so a failure can be reproduced locally.

Q5Do I need to write properties or fuzz targets first?

No. breakhound reads the types of each exported function, generates the inputs itself and checks built in rules on the results, so the first run needs no setup.
